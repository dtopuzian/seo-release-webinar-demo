# Две витрины и один незаметный дефект

Два лендинга показывают, как SEO-проверка останавливает ошибочный выпуск.
Сайт выглядит исправным и кнопка работает, но `meta robots noindex` запрещает
индексацию. Внешний вид v1 и v2 одинаков, меняется только индикатор версии.

- [Сайт №1: Без SEO-автотестов в CI/CD](https://shop.194-61-9-250.sslip.io:9443/)
- [Сайт №2: С SEO-автотестами в CI/CD](https://shop.194-61-9-250.sslip.io:9443/checked/)
- [Три запуска в Actions](https://github.com/dtopuzian/seo-release-webinar-demo/actions)
- [Бот SEO Checker](https://t.me/seo_release_checker_bot)

## Репетиция и показ

Перед показом запустите **«3. Вернуть обе витрины к v1»**, дождитесь зелёного
результата и убедитесь, что очередь Actions пуста. На обоих сайтах должна быть
**Версия v1**. Запускайте сценарии последовательно: ожидание очереди GitHub
отдельно от времени проверки.

1. Откройте сайт №1. Нажмите кнопку: ответ появится прямо на странице.
2. В Actions выберите **«1. Выпустить без SEO-проверки» → Run workflow**.
   После публикации обновите сайт №1: теперь это v2. Вид страницы и кнопка
   прежние, но в исходном HTML появился `noindex,follow`.
3. Запустите **«2. Выпустить с SEO-проверкой»**. В графе Actions четыре этапа:
   **Модульные тесты → Сборка → SEO-автотесты → Релиз**. Первые два станут
   зелёными, последние два — красными. «Релиз» объяснит отказ допуска:
   «Релиз заблокирован: SEO-проверки не пройдены. Публикация не выполнялась».
   На сайте №2 останется v1.
4. В Telegram придёт короткая фактическая причина остановки и ссылки
   **«Открыть запуск»**, **«Открыть отчёт»**. Откройте обе ссылки.
5. Через обычный интерфейс бота проверьте сайт №1 по корневому адресу.
   В отчёте найдите запрет индексации в разделе meta robots.
6. Снова запустите **«3. Вернуть обе витрины к v1»** и проверьте оба индикатора.
   Сброс не отправляет сообщения в Telegram. История запусков и отчёты остаются.

Полный цикл: **сброс → первый выпуск → второй выпуск → ручная проверка → сброс**.
На телефоне и компьютере проверьте оба лендинга, кнопки и короткие уведомления.

## Что именно проверяется

В каждом демонстрационном выпуске движок проверяет **только главную страницу**
соответствующего лендинга. Требуются HTTP 200, полный HTML и отсутствие
`noindex` или `none` в общем `meta robots`. Ошибка, неизвестный результат или
неполный HTML блокируют публикацию сайта №2. Охват обычных проверок через бота
этим ограничением не меняется.

Без проверки публикуется ошибочная v2 сайта №1. С проверкой такой же SEO-дефект
блокирует v2 сайта №2. При сбросе проверяются обе исправные главные страницы,
затем последовательно публикуются v1. `robots.txt` везде разрешает обход.
Noindex влияет на поиск после повторного обхода: показ иллюстрирует обнаружение
дефекта, а не мгновенное исчезновение страницы из поисковой выдачи.

Telegram сообщает только подтверждённую остановку SEO-проверкой: одну фактическую
причину и ссылку на запуск, без списка страниц и технической сводки. При неполной
проверке сообщение приходит, если текущий кандидат не опубликован. Ссылка на отчёт
есть только при наличии проверенного отчёта этого запуска.

Успешная публикация и сброс проходят без Telegram. Сбой SSH, некорректный JSON или
устаревшая квитанция тоже не вызывают сообщения: ошибка остаётся в Actions.
Этим веткам не нужны Telegram-секреты. Ошибка отправки необходимого уведомления
видна в шаге и никогда не разрешает публикацию или её повтор.

## Настройка ведущим

Три workflows запускаются вручную только в основной ветке репозитория
`dtopuzian/seo-release-webinar-demo`. Repository Actions secrets:

| Secret | Значение |
|---|---|
| `DEMO_SSH_KEY` | Выделенный OpenSSH-ключ демо без парольной фразы. |
| `DEMO_SSH_KNOWN_HOSTS` | Заранее проверенная запись ключа SSH-хоста. |
| `DEMO_TELEGRAM_TOKEN` | Токен бота для уведомлений ведущему. |
| `DEMO_TELEGRAM_CHAT` | Числовой ID личного чата ведущего. |

Секреты доступны только нужным шагам. SSH-файлы создаются временно с правами
0600 и удаляются после операции. Произвольного адресата в форме запуска нет.

В первом и третьем сценариях один job. Во втором четыре последовательных job:
модульные тесты без сети и секретов, однократная сборка кандидата v2 сайта №2,
SEO-проверка и проверка допуска к релизу. Между job передаётся только SHA-256
сборки. Каждый job получает один и тот же commit через закреплённый checkout.
Ошибка или пропуск тестов/сборки, пропуск SEO или отмена запуска не допускают релиз.
При отказе SEO job «Релиз» запускается только для явного отказа, без команды
публикации и без повторного уведомления. Ошибка самой публикации не выдаётся
за найденный SEO-дефект.
Все три сценария используют общую очередь без отмены активного запуска.
Параллельные команды оператора вне GitHub
в неё не входят. При частичном сбое сброса последний шаг получает свежий статус
обоих сайтов, не объявляя успешным весь сброс.

Проверка и публикация сверяют runtime SHA, текущий run ID, сайт, версию и digest.
Каждое уведомление получает свежую серверную квитанцию; старый PASS не используется.
После ошибки checkout клиент не запускается. Отмена останавливает следующие
шаги, но не означает автоматический откат уже принятой сервером операции.

Публикуются заранее установленные неизменяемые серверные артефакты. Во втором
сценарии digest локально собранных файлов обязателен: подготовка, проверка,
свежий статус, уведомление и релиз должны подтвердить тот же кандидат.
Отсутствующий или несовпадающий digest блокирует операцию. Даже при трёх успешных
job публикацию разрешает только свежий серверный статус и серверный допуск.
Правка HTML в GitHub сама по себе серверные артефакты не заменяет. Для демонстрации сервер
должен поддерживать отдельные `artifacts/{unsafe,checked}/{good,bad}`, проверку
одной главной и поля квитанции для фактической причины. Серверный runtime SHA
закрепляется в `DEMO_RUNTIME_SHA` во всех трёх workflows и отличается от SHA
публичного репозитория. Установка сервера выполняется отдельно до переключения
этого pin; старый runtime магазина не поддерживает новый сценарий.

Python-пакеты не устанавливаются, artifacts в GitHub не передаются. Единственный
внешний action — checkout v7.0.1, закреплённый SHA
`3d3c42e5aac5ba805825da76410c181273ba90b1`, без сохранения credentials.

Ориентиры активного выполнения: первый выпуск ≤25 с, цепочка с SEO ≤90 с,
сброс ≤65 с. Для четырёх job время выполнения и ожидание runner замеряются
отдельно по каждому этапу. Это цели для реального замера, а не гарантия очереди GitHub.

## Локальный просмотр и тесты

Python 3.12+, стандартная библиотека:

```sh
python build_shop.py good .work/unsafe --target unsafe
python build_shop.py good .work/checked --target checked
python build_shop.py bad .work/unsafe-v2 --target unsafe
python -m http.server 8787 --bind 127.0.0.1 --directory .work
```

Откройте `http://127.0.0.1:8787/unsafe/` или `/checked/`. Выходной каталог сборки
должен быть новым или пустым; уже собранные артефакты не перезаписываются.
Каждый лендинг состоит из одной HTML-страницы и локальных CSS, JS, PNG.
Ссылки относительные, поэтому одинаковые байты работают в корне и подпапке.
Каталога, корзины, покупок, внешних CDN, аналитики и персональных данных нет.

```sh
python -I -B -m unittest discover -s tests -v
```

Проверки покрывают четыре артефакта, воспроизводимый digest, точное отличие
v1/v2, единственную страницу и кнопку, квитанции, сбои SSH, отсутствие ложного
PASS, короткие уведомления и ссылки, изоляцию секретов и условия шагов workflow.
В тестах нет настоящего Telegram и публикаций на сервере.
Эти же проверки автоматически выполняются для PR и main без секретов и деплоя.
